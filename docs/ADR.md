# Architecture Decision Records

## 철학
MVP 속도 최우선. 관리형 서비스(Supabase, Vercel, Polar)로 인프라를 최소화하고, 첫 사용자에게 필요 없는 것은 만들지 않는다. 다만 금융 데이터를 다루므로 권한 분리, 서버 전용 키, 웹훅 서명 검증은 타협하지 않는다. LLM은 판단이 필요한 곳에만 쓰고, 계산은 코드로 한다.

---

### ADR-001: Next.js 16 App Router + TypeScript + Tailwind
**결정**: Next.js 16(App Router, `proxy.ts`) 단일 앱으로 프론트와 API를 구성한다.
**이유**: 별도 백엔드 없이 Route Handler로 충분하고 Vercel 배포와 궁합이 좋다.
**트레이드오프**: 함수 실행 시간(최대 300초)과 요청 본문(4.5MB) 제한을 받는다. 파일 한도와 동기 처리 설계로 제한 안에 맞춘다.

### ADR-002: 분석은 요청 한 번에 동기 처리
**결정**: `POST /api/analyses`가 업로드부터 저장까지 끝까지 처리한다(`maxDuration = 300`). Storage 직접 업로드, `after()` 비동기 처리, 상태 폴링은 쓰지 않는다.
**이유**: 파일당 1MB·최대 3개로 본문 한도 안에 들어오고, 폴링·업로드 2단계·중간 상태가 사라져 구현이 단순하다.
**트레이드오프**: 분석 중 다른 페이지로 가면 진행 표시를 못 본다(결과는 저장됨). 강제 종료된 분석은 6분 뒤 다음 접근에서 `failed/timeout`으로 정리한다.

### ADR-003: Supabase (Auth + Postgres + Storage), 금융 데이터는 서버 전용
**결정**: 인증·DB·파일을 Supabase(서울 리전)로 처리한다. 키는 publishable/secret 방식, 인증 확인은 `getClaims()`. 모든 테이블의 클라이언트 권한을 회수하고 서버(`lib/data`, secret key)에서만 조회하며, 모든 쿼리에 `user_id = claims.sub` 조건을 건다.
**이유**: 클라이언트가 PostgREST로 직접 조회하면 Free 사용자가 Pro 탐지 결과를 받아갈 수 있다. 서버에서 플랜별로 걸러낸 `AnalysisView`만 내보낸다.
**트레이드오프**: RLS가 아니라 애플리케이션 코드가 소유권을 지킨다. 소유권 조건 누락을 막기 위해 조회를 `lib/data` 한 곳으로 모은다.

### ADR-004: 결제는 Polar
**결정**: Polar 구독(Pro $9/월), `customerExternalId = Supabase user id`. 구독 상태 `active`·`trialing`·`past_due`를 Pro로 보고, `subscription.revoked`에서 Free로 바꾼다.
**이유**: Merchant of Record라 세금 처리를 대신 해준다. 해지해도 기간 끝까지 `active`로 유지되는 Polar 동작과 맞다.
**트레이드오프**: 한국어·원화 서비스인데 결제는 USD다. 국내 PG는 MVP 이후 검토한다.

### ADR-005: LLM은 플랜별 모델 (Free Sonnet 5.5, Pro Opus 5.5)
**결정**: Free 분석의 컬럼 매핑·가맹점 분류는 `claude-sonnet-5-5`, Pro 분석과 인사이트(Pro 전용)는 `claude-opus-5-5`를 쓴다. 모델은 분석 시작 시점의 플랜으로 정하고, `services/claude.ts`가 `plan`을 받아 `CLAUDE_MODEL_FREE`/`CLAUDE_MODEL_PRO` env에서 고른다. structured outputs + zod 검증.
**이유**: 무료 사용자 비용을 낮추고 응답을 빠르게 하면서, 유료 사용자에게는 가장 정확한 모델을 준다. 같은 프롬프트·스키마를 쓰고 모델 ID만 바꾸므로 코드 분기는 모델 선택 한 곳뿐이다.
**트레이드오프**: 두 모델 모두에서 매핑·분류 품질과 응답 시간을 확인해야 한다(go-live 단계 실측). Free와 Pro의 분류 결과가 조금 다를 수 있다.

### ADR-006: LLM 호출 최소화
**결정**: (1) 매핑은 헤더 + 샘플만 보낸다. (2) 분류는 고유 가맹점 단위로 100개씩 배치. (3) 합계·추이·정기결제·이상거래는 코드로 계산한다. (4) 인사이트는 Pro가 버튼을 누를 때만, 집계값만 보내서 생성한다.
**이유**: 비용·지연을 줄이고 계산 결과를 테스트로 검증할 수 있다.
**트레이드오프**: 규칙 기반 탐지는 LLM보다 유연하지 않다.

### ADR-007: 파일 파싱은 SheetJS + 엄격 디코딩
**결정**: SheetJS 0.20.3을 CDN tarball로 설치한다(npm `xlsx@0.18.5`는 CVE 2건). CSV·HTML-xls는 `TextDecoder('utf-8', {fatal:true})` → 실패 시 `TextDecoder('euc-kr', {fatal:true})`로 디코딩하고, 둘 다 실패하면 거부한다. `sheetRows: 1201`로 읽어 1,201번째 행이 있으면 거부한다. 행 상한은 이것 하나이고, 컬럼·셀 크기는 1MB 한도에 맡긴다.
**이유**: 국내 카드사·은행 파일(엑셀, HTML-xls, EUC-KR)을 추가 의존성 없이 처리하고, 깨진 글자나 잘린 결과로 분석하지 않는다.
**트레이드오프**: 첫 시트만 읽는다. 압축 해제 크기 사전 검사는 생략한다(1MB 입력, 실패해도 요청 하나만 영향).

### ADR-008: KRW 전용
**결정**: 원화만 지원한다. 매핑 단계에서 원화 금액 열을 고르고(해외 결제는 원화 환산 열), 원화 금액 열이 없으면 `unsupported_currency`로 거부한다. 금액은 원 단위 정수(`bigint`).
**이유**: 대상이 국내 카드·은행 명세서다. 통화 판정·혼합 통화 거부·통화별 추이와 그 테스트가 모두 사라진다.
**트레이드오프**: 외화 전용 명세서는 분석할 수 없다.

### ADR-009: 사용량은 성공만 기록하는 원장 + 사용자당 처리 1건
**결정**: `analyses(user_id) WHERE status='processing'` 부분 unique index로 동시 처리를 막고, 성공한 분석만 `analysis_usage`에 기록한다(분석 삭제와 무관하게 유지). 거래 저장·완료 전환·사용량 기록은 `completeAnalysis` RPC 한 트랜잭션에서 `status='processing'` 조건으로 수행한다.
**이유**: 예약 상태 관리나 사용자 잠금 없이도 동시 요청·삭제로 한도를 우회할 수 없고, 늦게 끝난 요청이 결과를 덮어쓰지 못한다.
**트레이드오프**: 사용자당 병렬 분석이 불가능하다.

### ADR-010: Free/Pro는 기능으로만 구분
**결정**: 누적 추이·다중 파일·탐지 상세·AI 인사이트를 Pro 전용으로 두고, 월 분석 횟수(5/50)는 남용 방지용으로만 둔다. Free도 자신의 모든 분석을 열람한다.
**이유**: 명세서는 월 1회라 횟수 제한은 차별점이 아니다. 분석 단위 잠금이 없으면 열람 권한 판정·잠금 응답·잠금 화면이 필요 없고, 다운그레이드·재구독 시 데이터가 그대로 보존된다.
**트레이드오프**: Free의 업그레이드 동기가 기능 잠금 카드에만 의존한다(H5로 측정). Free 사용자의 원본도 사용자가 지울 때까지 보관된다.

### ADR-011: 원본 파일 저장, 삭제는 Storage 먼저
**결정**: 원본을 private 버킷에 서버 생성 경로(`{user_id}/{analysis_id}/{upload_id}`)로 저장한다. 삭제는 Storage 삭제 확인 후 DB, 회원 탈퇴는 Polar 구독 취소 → Storage → auth 사용자 순서로 하고, 앞 단계가 실패하면 멈춘다.
**이유**: 파싱 실패 원인 분석과 재분석에 필요하다. 삭제 순서를 지켜 결제는 계속되는데 계정은 없거나, DB는 지웠는데 원본이 남는 상황을 막는다.
**트레이드오프**: 민감한 원본을 보관하는 책임. 업로드 화면·처리방침에 명시하고 로그에 내용을 남기지 않는다.

### ADR-012: 한국어 전용, i18n 없음
**결정**: UI는 한국어만 제공한다. i18n 라이브러리를 쓰지 않고, 에러 코드 문구만 `src/messages/errors.ts` 한 곳에 둔다. 인사이트도 한국어로 생성한다.
**이유**: 대상이 국내 명세서 사용자다. 로케일 결정·저장(`profiles`), 번역 파일 2벌, 인사이트 언어 저장이 사라지고 `proxy.ts`는 Supabase 세션 갱신만 한다.
**트레이드오프**: 영어 사용자는 받을 수 없다. 필요해지면 문자열을 메시지 파일로 옮긴다.

### ADR-013: Vercel CLI로 매 step 배포, Claude·Polar는 mock 먼저
**결정**: 각 구현 step의 AC 마지막에 `vercel deploy --prod`와 운영 도메인 200 확인을 넣는다. `MOCK_SERVICES=claude,polar` env가 있을 때만 mock을 쓰고(자동 감지 금지), 화면에 "데모 모드"를 표시한다. Supabase는 mock하지 않는다.
**이유**: 외부 계정 준비 전에도 배포된 URL에서 전체 흐름을 확인할 수 있다. 명시적 env만 인정해 운영에서 키 누락 시 가짜 결과가 나가는 것을 막는다.
**트레이드오프**: 출시 전까지 프로덕션 URL이 개발 중 상태로 공개된다. 결제를 켜는 시점에 Vercel Pro가 필요하다(Hobby는 상업적 이용 금지).

### ADR-014: 테스트는 Vitest, DB 통합 테스트는 최소
**결정**: Vitest + Testing Library로 단위·컴포넌트 테스트. DB 통합 테스트는 Supabase **개발용 클라우드 프로젝트**에 대해 권한 차단과 완료 RPC만 다룬다. Docker·pgTAP·E2E는 쓰지 않는다.
**이유**: 핵심 로직(`lib/`)은 순수 함수라 단위 테스트로 대부분 커버되고, DB에서만 확인 가능한 것은 권한과 트랜잭션뿐이다.
**트레이드오프**: 인증·결제 전체 흐름은 go-live 단계 수동 체크리스트에 의존한다.
