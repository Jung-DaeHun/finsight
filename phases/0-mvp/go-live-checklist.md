# Step 15 운영 전환 검증

운영 URL: https://finsight-orcin-two.vercel.app

자동 실행 결과와 사용자가 직접 확인할 항목을 구분한다. 아래 수동 항목은 실제 브라우저·대시보드·샌드박스 결제로 확인한 뒤 체크한다. 환경 변수 값과 시크릿은 이 문서에 기록하지 않는다.

## Claude 응답 시간 실측

2026-10-04(KST)에 `.env.go-live.local`의 API 키를 해당 프로세스에만 주입하고, `MOCK_SERVICES`를 비운 상태로 `npm run measure:claude`를 두 번 실행했다. 모델별 매핑 1회와 가상의 고유 가맹점 100개 분류 1회를 측정했다.

| 실행 | 모델 / 플랜 | 매핑 | 100개 분류 | 최대 입력 예상 | 240초 기준 |
|---|---|---:|---:|---:|---|
| 조정 전, 동시 2개 | `claude-sonnet-5-5` / Free | 4,356ms | 9,636ms | 62,170ms | 통과 |
| 조정 전, 동시 2개 | `claude-opus-5-5` / Pro | 2,976ms | 14,795ms | 275,239ms | 초과 |
| 확정, 동시 3개 | `claude-sonnet-5-5` / Free | 1,768ms | 9,512ms | 39,816ms | 통과 |
| 확정, 동시 3개 | `claude-opus-5-5` / Pro | 2,998ms | 14,402ms | 181,814ms | 통과 |

최대 입력은 모든 행에 서로 다른 가맹점이 있다고 가정한다. 현재 파이프라인은 파일별 매핑·분류를 순서대로 실행하므로 예상 시간은 `파일 수 × (매핑 시간 + ceil(ceil(1,200 / 100) / 3) × 분류 시간)`이다. Free는 1파일·1,200행·분류 4라운드, Pro는 3파일·3,600행·분류 총 12라운드다. 표의 시간은 스크립트 출력이며, 계산에는 반올림 전 측정값을 사용했다.

`src/services/claude-config.ts` 확정값:

- 호출별 timeout: **60,000ms**. 가장 느렸던 100개 분류(14,795ms)에 여유를 두고 기존 60초를 유지했다.
- SDK 재시도: **1회**.
- 분류 배치: **100개**, 동시 호출: **3개**. Pro 예상 시간을 240초 아래로 낮추기 위해 기존 2개에서 조정했다.
- `max_tokens`: 기존 **16,000** 유지. 분석 Route Handler의 `maxDuration = 300`도 유지한다.

예상 시간은 성공한 Claude 호출의 외삽이다. 실제 동시 호출의 속도·제한, 재시도, 파일 업로드·파싱·Storage·DB 시간은 포함하지 않으므로 최대 입력의 실제 완료 시간은 아래 수동 항목으로 별도 확인한다. (J2, J5, R5)

## 전체 사용자 흐름 — 사용자 확인

순서: 이메일 가입 → 다른 기기에서 인증 링크 열기 → 샘플 → 실제 명세서 → 결과 → Polar 샌드박스 결제 → Pro 기능 → 포털에서 해지 → 회원 탈퇴.

- [ ] 운영 환경에서 이메일 계정 A·B를 만든다. A의 가입 인증 링크를 가입한 기기와 다른 기기에서 열어 대시보드로 이동하는지 확인한다. 비로그인 보호 경로도 확인한다. (J1)
- [ ] 비밀번호 재설정 이메일 링크와 Google 로그인으로 대시보드에 도착하는지 확인한다. (J1)
- [ ] 로그인 전·후 공개 샘플을 확인한다. 샘플은 실제 Claude 호출 없이 KPI·거래·추이·Pro 표시를 렌더해야 한다. (J1, J3, R8)
- [ ] 국내 카드사 엑셀 3종과 은행 거래내역 1종을 각각 별도 설정 없이 분석한다. 제목·합계·취소·분리 입출금·한글 인코딩·원화 환산 열을 원본과 대조한다. `transfer`·`income`은 지출 합계에서 제외되어야 한다. (J2, J3, R3, R6, R7)
- [ ] 분석 결과의 총지출·카테고리·가맹점·일반 거래 목록이 원본과 일치하는지 확인한다. Free에는 탐지 건수만, Pro에는 상세·거래일 기준 추이·전월 대비가 보여야 한다. 모바일에서도 확인한다. (J3, R8)
- [ ] A의 Free 결과 페이지 HTML/RSC에서 **분석 데이터 객체**에 `isRecurring`·`anomalyType`, 탐지 `items`, `trend`, `insights` 필드가 없는지 확인한다. 화면용 문자열·컴포넌트명과 데이터 필드를 구별하고, 다운그레이드 후 저장된 인사이트도 확인한다. (J3, J6, R4)
- [ ] B로 로그인한 상태에서 A의 분석 ID를 결과 페이지, `DELETE /api/analyses/{id}`, `POST /api/analyses/{id}/insights`에 사용한다. 모두 알 수 없는 ID와 동일한 404여야 한다. (J3, J7, R1, R4)
- [ ] Free와 Pro의 인증 토큰으로 운영 테이블의 직접 SELECT/INSERT/UPDATE/DELETE 및 완료 RPC 실행이 거부되는지 확인한다. 운영 DB에 자동 통합 테스트를 실행하지 않는다. (J3, J7, R1, R4)
- [ ] 분석 중 버튼 재클릭·다른 탭의 추가 업로드가 사용자당 처리 1건 제한으로 막히는지 확인한다. 실패한 분석은 횟수를 차감하지 않아야 한다. (J2, R2)
- [ ] 업로드가 서버에 도착한 뒤 분석 중 탭을 닫고 다시 대시보드에서 완료 결과가 저장됐는지 확인한다. 연결 종료만으로 분석이 취소되면 안 된다. (J2, 2.1, R5)
- [ ] 6분 넘게 남은 processing은 다음 대시보드·상세·업로드·삭제 접근에서 failed/timeout이 되는지 확인한다. (J2, 2.2, R5)
- [ ] Polar 샌드박스 결제로 Pro 전환을 확인한다. 결제 확인의 완료 상태와 기존 분석의 탐지 상세·추이·인사이트 생성 버튼 해제를 확인한다. (J4, R4, R8)
- [ ] Pro로 실제 인사이트를 생성하고 새로고침 후 유지되는지 확인한다. 생성 실패가 이미 성공한 분석의 상태·사용량을 바꾸지 않아야 한다. (J3, J5, R5, R8)
- [ ] Pro 최대 입력인 **3파일·3,600행** 분석이 업로드 시작부터 결과까지 **240초 이내**에 완료되는지 실제로 측정하고 시간을 기록한다: `____초`. Free 최대 입력(1파일·1,200행)도 기록한다: `____초`. (J2, J5, R3, R5, PRD 성공 기준)

- [ ] 분석을 개별 삭제하고 원본 Storage·DB 결과 삭제, 해당 결과 404, 사용량 유지 여부를 확인한다. (J7, R1, R2)
